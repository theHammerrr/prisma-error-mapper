# Prisma 6.14 verification

Checked 2026-09-27. Baseline: npm `@prisma/client@6.14.0`, TypeScript 5.9.2. The v6 documentation is version-scoped, while Git tags below pin the exact source baseline.

- [Prisma v6 error reference](https://www.prisma.io/docs/orm/v6/reference/error-reference): confirms the four supported error semantics and distinct client error classes. Documentation message placeholders do not establish guaranteed client metadata fields.
- [Known request class, tag 6.14.0](https://github.com/prisma/prisma/blob/6.14.0/packages/client/src/runtime/core/errors/PrismaClientKnownRequestError.ts): `code` and `clientVersion` are strings; `meta` is an optional record of unknown values; `batchRequestIdx` is optional and non-enumerable.
- [Initialization class, tag 6.14.0](https://github.com/prisma/prisma/blob/6.14.0/packages/client/src/runtime/core/errors/PrismaClientInitializationError.ts): optional `errorCode`; no declared metadata or `code`.
- [Query engine errors, tag 6.14.0](https://github.com/prisma/prisma-engines/blob/6.14.0/libs/user-facing-errors/src/query_engine/mod.rs): P2002 serializes a constraint under `target`. Its untagged enum permits field arrays, index strings, and null unit variants. P2015 carries `details`; P2025 carries `cause`.
- [Request handler, tag 6.14.0](https://github.com/prisma/prisma/blob/6.14.0/packages/client/src/runtime/RequestHandler.ts): can add `modelName` when constructing known request errors. It is not a universally present engine field.
- [Common engine errors, tag 6.14.0](https://github.com/prisma/prisma-engines/blob/6.14.0/libs/user-facing-errors/src/common.rs): schema parser errors use P1012. An engine diagnostic is not necessarily exposed as client metadata; no convenience fields are invented for it.
- [Native PostgreSQL conversion, tag 6.14.0](https://github.com/prisma/prisma-engines/blob/6.14.0/quaint/src/connector/postgres/native/error.rs): database errors are converted from `tokio_postgres::DbError` to Prisma's flattened `PostgresError` before the generic query-error branch.
- [PostgreSQL error mapping, tag 6.14.0](https://github.com/prisma/prisma-engines/blob/6.14.0/quaint/src/connector/postgres/error.rs): unrecognized SQLSTATE values such as 23514 become a query error containing that flattened `PostgresError`.
- [PostgreSQL ErrorResponse fields](https://www.postgresql.org/docs/current/protocol-error-fields.html): schema, table, and constraint are distinct optional object fields; `file`, `line`, and `routine` identify the PostgreSQL server source-code location.

The installed `runtime/library.d.ts` and direct runtime constructors are checked during implementation and unit tests. Unit tests instantiate actual classes without generating a Prisma client or connecting to a database. Handler metadata is explicitly a package-generated validated view. The original object remains unmodified.

## PostgreSQL integration observations

`npm run test:integration` uses generated Prisma Client/CLI 6.14.0 and a digest-pinned PostgreSQL 16.15 container. For this change on Windows, Node 22.16.0 passed all 38 unit tests, 24 integration tests, TypeScript checks, and the build. CI also runs Node 22 and 24 on Linux.

Both explicit and generated unique-index/constraint names yield P2002 `target` arrays of database columns. A mapped `externalId` field yields `external_id`; compound constraints preserve the observed column order. Constraint names are verified independently through PostgreSQL catalogs.

A model mapped with `@@schema("billing")` and a named CHECK is exercised through the generated client. Prisma's PostgreSQL diagnostic identifies its table as `BillingConstraint` without a schema name; the parser and table/constraint handler work, but cannot distinguish identical table and constraint names in different schemas.

The separately captured nested `QueryError(Error { kind: Db, cause: Some(DbError { ... }) })` sample is accepted defensively and covered by a deterministic parser fixture. The 6.14 native connector source and this repository's live 6.14 integration run both point to the flattened `PostgresError` shape for a database CHECK failure, so the nested sample is not established as output of the bundled Prisma 6.14 native engine. The 6.14 JavaScript unknown-request class stores an arbitrary message and can transport either text shape, but the class alone does not establish which engine produced it. The `d:\\pginstaller_12.auto\\...` value is PostgreSQL's server source-file diagnostic, not evidence that Node, Prisma Client, or the parser ran on Windows.

When the nested format supplies schema, table, and constraint fields, the parser validates table and constraint against the primary message and validates schema when the primary relation is actually schema-qualified. It exposes the structured schema separately as optional `schemaName`; it never changes an unqualified `"product"` relation into `public.product`. Handler routing remains keyed by table and constraint for compatibility. A focused unit case also covers an actual `"schema"."table"` primary relation.

The SQL CHECK constraint `"check normal email"` rejects emails beginning with `123`. Prisma ORM create/update exposes this as `PrismaClientUnknownRequestError`: the diagnostic message includes SQLSTATE 23514 and the constraint name, but the error has no structured `code` or `meta`. A raw SQL violation instead yields known-request P2010 with `meta.code` equal to `23514` and diagnostic `meta.message`. Default handling preserves both errors. Configuring named `constraints` handlers opts into parsing and direct mapping; `parsePrismaPostgresError` also remains separately callable. Derived diagnostics never add fields to Prisma metadata. The fixture verifies parsing, direct constraint mapping, rejected inserts/updates, unchanged data following rejection, allowed non-prefix occurrences, and the exact catalog constraint name. In 0.2.0 unmatched Prisma errors use `onUnhandledPrismaError`; only unrelated inputs use `fallback`.

The Windows-origin nested case is a captured-format unit test, not a live test against a Windows PostgreSQL server. The Testcontainers integration database remains the digest-pinned Linux PostgreSQL 16.15 image and must not be used as evidence for Windows-server emission behavior.

Missing reads/updates/deletes and a nested connect emit P2025. An invalid datasource protocol emits initialization P1012 with `errorCode` and no raw metadata. A raw SQL duplicate instead emits P2010 with SQLSTATE 23505, and foreign-key violations emit P2003. Batch failures retain a non-enumerable request index. These observations are assertions in `tests/integration/postgres.test.ts`, not inferred guarantees for every provider.
